# План интеграции онлайн-оплаты через ЮKassa

## Цель

Добавить в «Таваар Доставка» оплату банковской картой и другими способами, которые доступны в магазине ЮKassa, не передавая данные карт через приложение и не объявляя заказ оплаченным по одному факту возврата пользователя из платёжной формы.

Источником истины для денег будет сервер: клиент передаёт только состав заказа и выбранный способ оплаты, backend заново проверяет ресторан и блюда, считает сумму в копейках, создаёт платёж в ЮKassa и переводит внутренний платёж в успешное состояние только после подтверждения статуса ЮKassa через API или валидного webhook-события.

## Что подтверждено документацией ЮKassa

API ЮKassa работает через `https://api.yookassa.ru/v3/`. Для обычного магазина применяется HTTP Basic Auth: идентификатор магазина передаётся как имя пользователя, секретный ключ — как пароль. Секреты должны находиться только на сервере и не попадать в Expo bundle, браузер, Git или логи. [Формат взаимодействия с API ЮKassa](https://yookassa.ru/developers/using-api/interaction-format)

Для POST и DELETE нужно передавать заголовок `Idempotence-Key`. ЮKassa рекомендует UUID v4 и сохраняет результат идемпотентного запроса в течение 24 часов. HTTP 500 сам по себе не подтверждает ни успех, ни неуспех финансовой операции, поэтому после неопределённого ответа нужно запросить объект платежа по API. [Формат взаимодействия с API ЮKassa](https://yookassa.ru/developers/using-api/interaction-format)

Для платежей понадобятся события `payment.waiting_for_capture`, `payment.succeeded` и `payment.canceled`; для возвратов — `refund.succeeded`. Уведомление содержит `type`, `event` и `object`. Webhook должен отвечать HTTP 200, иначе ЮKassa будет повторять доставку уведомления в течение 24 часов. Для HTTP Basic Auth подписка на уведомления настраивается в личном кабинете магазина; URL должен быть HTTPS на порту 443 или 8443 с TLS 1.2+. Подлинность следует проверять по текущему статусу объекта через API и дополнительно ограничивать входящие запросы опубликованными IP-диапазонами ЮKassa. [Входящие уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks)

## Архитектура

### 1. Provider adapter

Создать `server/payments/yookassa.ts` с изолированным адаптером. Остальной backend не должен собирать HTTP-запросы к ЮKassa напрямую. Адаптер должен предоставлять операции:

- `createPayment({ orderId, amountKopecks, description, returnUrl, receipt })`;
- `getPayment(paymentId)`;
- `createRefund({ paymentId, amountKopecks, idempotencyKey, receipt })`;
- преобразование ответа ЮKassa в внутренние статусы без публикации сырых ответов в логи.

Сумма переводится из целых копеек в строковый RUB-формат с двумя знаками после запятой только на границе с API. Обратное преобразование должно проверять валюту `RUB`, не допускать отрицательную сумму и сохранять целое количество копеек без плавающей арифметики.

### 2. Секреты и конфигурация

Добавить защищённые production-переменные:

- `YOOKASSA_SHOP_ID` — идентификатор магазина;
- `YOOKASSA_SECRET_KEY` — секретный ключ API;
- `YOOKASSA_RETURN_URL` — HTTPS URL возврата в приложение, например `https://tavaar.online/order/payment-return`;
- `YOOKASSA_WEBHOOK_IP_ALLOWLIST` — конфигурация опубликованных CIDR-диапазонов, если allowlist не будет зашит в адаптер;
- `YOOKASSA_ENABLED` — явный флаг включения онлайн-оплаты после тестовой проверки.

В `.env.example` добавить только имена и пояснения без значений. В production при отсутствии обязательных секретов онлайн-оплата должна оставаться выключенной, а интерфейс — показывать тот же честный fallback, который сейчас используется для наличных. Нельзя включать оплату автоматически только из-за наличия одного секрета.

### 3. Модель данных

Текущего `orders.paymentMethod='cash'` недостаточно для отслеживания онлайн-платежа. Добавить отдельную таблицу `payments`, чтобы история попыток не терялась:

- `id` — внутренний идентификатор;
- `orderId` — внешний ключ на заказ;
- `provider` — `yookassa`;
- `providerPaymentId` — уникальный ID платежа ЮKassa;
- `status` — `pending`, `waiting_for_capture`, `succeeded`, `canceled`, `failed`, `refunded`, `partially_refunded`;
- `amountKopecks`, `currency` — зафиксированная сумма и валюта;
- `idempotencyKey` — уникальный ключ операции создания платежа;
- `paymentMethodType` — тип платёжного инструмента без хранения реквизитов карты;
- `failureCode`/`failureMessage` — безопасные технические значения без персональных данных;
- `createdAt`, `updatedAt`, `succeededAt`, `canceledAt`.

В заказе добавить `paymentStatus`, `paidKopecks` и, при необходимости, `paidAt`. `orders.totalKopecks` остаётся полной server-authoritative суммой заказа и никогда не берётся из данных клиента. Для webhook-дедупликации добавить `payment_webhook_events` с уникальным ключом по `provider + event + providerObjectId + objectStatus`, временем получения и результатом обработки. Сырые payload не хранить без необходимости; если аудит требует payload, удалить токены, персональные данные и данные платёжного инструмента перед сохранением.

### 4. Создание онлайн-платежа

Текущую процедуру `customerOrders.create` расширить способом `online`, но не отправлять сумму из клиента. Рекомендуемый flow:

1. Пользователь выбирает «Онлайн-оплата» в checkout.
2. `customerOrders.create` в транзакции проверяет авторизацию, active-ресторан, доступность блюд, цены, количество, адрес, fulfillment и idempotency key. Создаётся заказ с `paymentStatus='pending'` и фиксированной суммой.
3. Backend создаёт запись `payments` и вызывает `POST /v3/payments` с новой UUID v4 в `Idempotence-Key`.
4. В запрос передаются server-calculated `amount`, `currency=RUB`, `capture=true`, понятное описание, `metadata.orderId`, `metadata.internalPaymentId` и `confirmation` с `return_url`.
5. Сохраняются только `providerPaymentId`, статус, сумма, тип подтверждения и URL подтверждения. Клиент получает URL подтверждения и открывает его во внешнем браузере или поддерживаемом WebView.
6. Если API вернул неопределённый ответ, backend сначала повторяет запрос с тем же ключом либо делает `GET /v3/payments/{id}` по сохранённому ID. Новый ключ для той же попытки создавать нельзя.

Чтобы повторная отправка checkout не создавала второй заказ, сохраняется текущая идемпотентность заказа. Чтобы повторный вызов создания платежа не создавал второе списание, используется отдельный стабильный `payments.idempotencyKey`, привязанный к одной внутренней попытке платежа.

### 5. Возврат пользователя из платёжной формы

Добавить маршрут возврата, например `/order/payment-return`. Этот экран не показывает «оплачено» по query-параметру и не доверяет только redirect. Он запрашивает защищённую процедуру `customerOrders.paymentStatus({ orderId })`, которая возвращает внутренний статус после серверной сверки с ЮKassa.

Состояния интерфейса:

- `pending` или `waiting_for_capture`: «Проверяем оплату» с кнопкой обновить;
- `succeeded`: «Оплата подтверждена», номер заказа и кнопка в историю;
- `canceled`/`failed`: заказ не оплачен, предложить повторить оплату с новой попыткой, не создавать второй заказ автоматически;
- неизвестное состояние: нейтральное сообщение и повторная проверка.

Экран успешного заказа из третьей итерации оставить для наличных. Для онлайн-платежа использовать тот же editorial-компонент, но показывать подтверждение только при `paymentStatus='succeeded'`.

### 6. Webhook endpoint

Добавить публичный endpoint `POST /api/payments/yookassa/webhook` в Express до tRPC-маршрутов. В Nginx добавить проксирование `/api/payments/` на backend и проверить, что endpoint доступен только по HTTPS.

Обработка должна быть короткой и идемпотентной:

1. Проверить HTTP-метод, размер body и JSON-схему.
2. Проверить IP отправителя по актуальному allowlist ЮKassa, если эта защита включена на deployment edge. Не логировать весь payload.
3. Проверить `event`, тип объекта, `object.id`, валюту и числовую сумму.
4. Получить текущий объект платежа через API ЮKassa и использовать его статус, сумму, валюту и metadata как источник истины. Само уведомление считать триггером, а не доказательством оплаты.
5. В транзакции зарегистрировать событие в `payment_webhook_events`. Если это дубликат, вернуть HTTP 200 без повторного начисления, уведомления или изменения заказа.
6. Сопоставить `providerPaymentId`, `metadata.orderId`, внутренний заказ и зафиксированную сумму. Любое несовпадение отправить в безопасный журнал ошибок и не переводить заказ в оплаченный статус.
7. Применить допустимый переход статуса:
   - `payment.waiting_for_capture` → `waiting_for_capture`;
   - `payment.succeeded` → `succeeded`, `paidKopecks=amountKopecks`, `paidAt=now`;
   - `payment.canceled` → `canceled` и `orders.status='payment_error'`, если заказ ещё не передан в приготовление;
   - `refund.succeeded` → `refunded` или `partially_refunded` по накопленному размеру возврата.
8. Создать уведомление пользователю и post-commit WebSocket/push-событие без платёжных реквизитов.
9. Вернуть HTTP 200 после безопасной фиксации события. Для временной недоступности базы лучше использовать контролируемый не-2xx ответ, чтобы ЮKassa повторила доставку, а не терять платёжное событие.

### 7. Захват, отмена и возвраты

На первом этапе использовать `capture=true`, чтобы после успешной авторизации деньги зачислялись без отдельной операции захвата. Если бизнес-процессу понадобится сначала подтверждение ресторана, перейти на `capture=false`: тогда `payment.waiting_for_capture` будет означать авторизованный, но ещё не списанный платёж; нужно будет добавить server-only процедуру захвата и таймер отмены истёкших заказов.

Возврат разрешать только server-side после проверки роли, заказа, допустимого статуса ресторана и доступного остатка к возврату. Каждая операция возврата получает собственный UUID `Idempotence-Key`, запись в таблице возвратов и связь с исходным платежом. Нельзя возвращать сумму, превышающую подтверждённую оплату за вычетом предыдущих успешных возвратов. Webhook `refund.succeeded` завершает переход; запрос на создание возврата сам по себе не означает, что деньги возвращены.

### 8. Чеки и 54-ФЗ

До production включения нужно определить, кто является продавцом по каждой операции, какой магазин ЮKassa формирует чек, какие ставки НДС и предметы расчёта применяются, а также какие контактные данные покупателя используются для чека. При подключённой онлайн-кассе в платёж нужно передавать позиции из server-side `order_items` с названием, количеством, ценой, `vat_code`, `payment_subject` и `payment_mode` по согласованной бухгалтерской схеме. Нельзя подставлять юридические параметры в код без подтверждения владельца магазина и бухгалтера. Официальный раздел ЮKassa отдельно описывает чеки и интеграцию с онлайн-кассой. [Чеки ЮKassa](https://yookassa.ru/developers/solutions-for-businesses/receipts)

### 9. API и права доступа

Добавить tRPC-процедуры:

- `customerOrders.createOnlinePayment` — создаёт платёж только владельцу заказа и возвращает confirmation URL;
- `customerOrders.paymentStatus` — возвращает безопасный статус только владельцу заказа;
- `adminPayments.refund` — отдельная роль и отдельная проверка права на возврат;
- `adminPayments.get` — внутренний просмотр без секретного ключа и без карточных данных.

Webhook не должен быть tRPC protected procedure: ЮKassa не имеет пользовательской сессии. Он должен использовать отдельную схему входной валидации, IP/API-проверки, дедупликацию и минимальный ответ.

### 10. Логи и безопасность

В логи разрешены только `orderId`, внутренний payment ID, provider payment ID в усечённом виде, событие, переход статуса, HTTP-код и correlation ID. Нельзя писать `YOOKASSA_SECRET_KEY`, authorization header, полные payment object, confirmation URL, телефон, email, маску карты или полный webhook payload.

В production запускать онлайн-оплату только если настроены HTTPS, secrets, webhook URL, database migration, clock synchronization, ограничение body size, rate limiting для пользовательских payment endpoints и мониторинг повторных/необработанных webhook. Не принимать решение о доставке только на клиентском redirect.

## Этапы реализации

### Этап A — подготовка магазина

Создать тестовый магазин ЮKassa, получить shop ID и тестовый секретный ключ, настроить HTTPS webhook на `https://tavaar.online/api/payments/yookassa/webhook`, включить события платежей и возвратов, проверить return URL и тестовые карты из документации. Production ключи не передавать в чат и не коммитить.

### Этап B — backend и миграции

Добавить adapter, таблицы платежей, возвратов и webhook events, payment status в orders, безопасные конфиги, tRPC procedures и Express webhook route. Написать переходы статусов и транзакционную дедупликацию. На этом этапе UI всё ещё должен скрывать онлайн-оплату, пока не пройдены тесты.

### Этап C — frontend checkout

Добавить опцию «Онлайн-оплата» только при `YOOKASS_ENABLED=true`. После создания платежа открыть confirmation URL. Добавить экран возврата и состояния pending/succeeded/canceled/unknown. Наличные оставить без изменения. Обновить историю заказа, чтобы она отображала «Оплачено онлайн» только для server-confirmed `succeeded`.

### Этап D — webhook и возвраты

Провести тесты повторной доставки, изменения статуса, неверной суммы, неверного metadata, неизвестного события, недоступной базы и повторного возврата. Затем подключить admin-only возврат с идемпотентностью и webhook `refund.succeeded`.

### Этап E — production rollout

Сначала включить `YOOKASS_ENABLED=false`, применить миграции и развернуть код. Затем проверить health endpoint, регистрацию webhook и тестовые платежи. После подтверждения всех acceptance checks включить флаг, выполнить один малый боевой платёж, сверить платёж в личном кабинете ЮKassa и только после этого объявить интеграцию готовой.

## Acceptance criteria

Готовой интеграция считается только если:

1. Клиент не может изменить сумму, валюту, состав заказа или metadata платежа.
2. Повторный tap, retry после таймаута и повторная доставка webhook не создают второй заказ, второй платёж, повторное уведомление или повторное начисление.
3. Нельзя показать «Оплачено» по redirect без server-side `payment.succeeded` и проверки суммы/RUB/order metadata.
4. Платёж с несовпадающей суммой, валютой, заказом или неизвестным provider ID не меняет оплаченный статус.
5. `payment.canceled` и технический failure дают понятное состояние для повторной оплаты без потери заказа.
6. Полный и частичный возврат имеют отдельные idempotency keys, не превышают оплаченный остаток и завершаются только после подтверждения ЮKassa.
7. Webhook доступен по HTTPS, отвечает 200 после идемпотентной обработки и корректно переживает повторную доставку.
8. Секреты не попадают в frontend, Git, миграции, логи и ответы API.
9. Чеки и юридическая модель подтверждены до боевого запуска.

## Открытые решения до начала разработки

Нужно подтвердить, будет ли ресторан подтверждать заказ до списания денег. По умолчанию план использует `capture=true`, что проще и безопаснее для первой версии; модель с `waiting_for_capture` потребует серверной операции захвата и фонового контроля сроков.

Также нужно получить юридические и бухгалтерские параметры магазина ЮKassa: продавец, онлайн-касса, НДС, предмет и способ расчёта в чеке. Без этих данных можно реализовать тестовый платежный контур, но нельзя честно объявлять production-фискализацию готовой.
